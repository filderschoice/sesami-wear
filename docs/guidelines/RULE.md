# Copilot / Claude Code 汎用フレームワーク

本書は、複数プロジェクトで再利用可能な AIコーディングエージェント（GitHub Copilot、Claude Code など）
応答生成の汎用フレームワークです。

## 存在意義

このドキュメントは、プロジェクト固有の運用ルール（`.github/copilot-instructions.md` および `CLAUDE.md`）のベースとなる「骨組み」を提供します。以下の項目を統一基準として複数プロジェクトで適用できます：

- 実装提案の基本原則（MUST/SHOULD）
- 推奨される出力フォーマット
- 完了条件（Definition of Done）
- 要件トレーサビリティの考え方

## 適用対象

- Copilot・Claude Code などのAIコーディングエージェントによる実装提案、コード生成、差分提案
- 初回実装・追加実装の両方
- 複数プロジェクトで共有可能な汎用指針

## 基本原則

AIコーディングエージェントによる応答生成は以下の原則に従います：

- MUST: 実装に直結する粒度で回答する
- MUST: 未確認事項は「未確認」と明示する
- MUST: 実現困難な要求は、理由・代替案・影響範囲を示す
- SHOULD: 暗黙の仕様変更を避け、既存仕様の維持有無を明記する
- SHOULD: 破壊的変更がある場合は段階的移行案を示す

## 実装モード別ルール

詳細は `.github/copilot-instructions.md`（Copilot）または `CLAUDE.md`（Claude Code）の「開発プロセス要件」を参照してください。

### 初回実装

実装提案には以下の項目が必須です：

- プロジェクト構成
- 主要ファイルの完全コード
- セットアップ・ビルド・実行・テスト手順
- 配布・更新・ロールバック方針

### 追加実装

実装提案には以下の項目が必須です：

- 変更対象ファイル一覧
- 各ファイルの差分
- 追加・変更テスト
- 互換性影響と移行手順
- 既存機能へのリグレッションリスク
- スキーマ変更時はマイグレーション方針

### 仕様変更の扱い

- 追加実装時に明示されていない要件は既存仕様を維持する（暗黙の仕様変更を禁止）
- 破壊的変更がある場合は段階的移行案を示す

### 自律ループ実行モード

人の応答を待たずに複数イテレーションを連続実行するモードです。採用する場合は、
プロジェクト側で以下をすべて定義してください（未定義のまま運用しないでください）。

- MUST: 適用条件（ユーザーの明示指示、作業ブランチ上での実行）
- MUST: 許可されるgit操作の範囲と、禁止される操作（`push`・規定ブランチへのコミット等）
- MUST: 停止条件（禁止操作への到達、品質ゲートの連続失敗、実行可能タスクの枯渇、完了）
- MUST: 人への確認が必要な事項の非同期化手順（確認質問の代替となる記録方法）
- MUST: 自動実行可能な品質ゲートのコマンドと、その合否判定基準
- MUST: ループの完了条件（Definition of Done）と、自動検証できない項目の除外方法
- MUST: 秘密情報の取り扱い（本番資格情報を用いる検証を自動実行しないこと）
- SHOULD: 対話前提の出力要件を、ファイル成果物・記録ファイルへ読み替える対応表

統制要件は `rules/guardrails-unified.v1.md` セクション12を参照してください。

## 品質・セキュリティ・データ保護

詳細は `.github/copilot-instructions.md`（Copilot）または `CLAUDE.md`（Claude Code）の以下セクションを参照してください：

- 「セキュリティ要件」: 秘密情報・入力検証・方針上書き対策
- 「品質・信頼性要件」: 品質ゲート・データ保護・耐障害性
- 「データ保護」: ログ・入力・通信の制御

## ドキュメント管理

詳細は `.github/copilot-instructions.md`（Copilot）または `CLAUDE.md`（Claude Code）の「ドキュメント管理要件」を参照してください。

- `docs/records/spec/FORMAT.md`: records記述仕様（唯一の参照元）
- `docs/records/managed/DESIGN.md`: 実装済み内容を統合した再実装用プロンプト設計書（最新版）
- `docs/records/managed/EXECUTE.md`: コード修正を伴う変更のみ記録
- `docs/records/managed/BACKLOG.md`: 未対応事項・課題・次ステップ

## 要件トレーサビリティ

実装完了時には以下を明示してください：

- MUST: 要件ごとに「対応済み/未対応/対象外」を明示する
- MUST: 未対応/対象外には理由と暫定対応を付記する
- MUST: 追加実装時は「今回変更する要件」を明示し、未記載要件は既存維持として扱う

## 推奨出力フォーマット

実装提案は以下の順で構成することを推奨します：

1. 実装方針
2. 技術選定方針
3. 対応範囲宣言
4. 変更対象一覧
5. 実装コード（初回: 全文 / 追加: 差分）
6. セットアップ/ビルド/実行手順
7. テスト項目
8. 品質ゲート実行結果
9. リリース/運用手順
10. 要件対応表（トレーサビリティ）
11. 既知課題・リグレッションリスク・次ステップ
12. 手動確認チェックリスト

## Definition of Done（完了条件）

実装提案が完了したと判定される条件：

- 実装、実行手順、テスト観点、既知課題がそろっている
- 要件対応表に抜け漏れがない
- 主要ユースケースの成功時/失敗時挙動を説明できる
- 品質ゲート結果（成功/失敗と根拠）を提示できる

自律ループ実行モードでは、上記に加えて以下も満たす必要があります：

- 未完了タスクが「人手検証待ち」「要確認」のみになっている
- 各イテレーションの実施記録が残っている
- 自動検証できなかった範囲が明示されている

## 運用メモ

- 本書は汎用フレームワークです。プロジェクト固有の制約・運用は `.github/copilot-instructions.md`（Copilot）または `CLAUDE.md`（Claude Code）で補完してください
- ルール更新時は差分理由を記録し、必要に応じて `CHANGELOG.md` 更新を提案してください
