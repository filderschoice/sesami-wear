# サブエージェントへ委ねる自律ループの進め方

1つの会話で実装まで行うと、読んだファイルやビルドの出力が会話に残り、以降のすべてのターンで再送されます。
会話を持つエージェント（オーケストレータ）が作業管理だけを行い、実装を担当へ渡すと、会話に残るのは委任文と
30行程度の報告だけになります。

統制要件（禁止操作・停止条件・要確認の扱い）は `rules/guardrails-unified.v1.md` セクション12、委任時の統制
（権限を広げない、委任先の報告を承認とみなさない、判断の集約、委任文の原文、監査、書き込む担当を同時に動かさない）は
同 12.7、イテレーション手順と分担の取り決めは Skill `autonomous-loop` が正本です。本スキルは複製せず、進め方だけを扱います。
適用条件は自律ループ実行モードと同じで、ユーザーが開始を明示的に指示していること、加えてサブエージェントへの
委任をユーザーが指示していることです。`.claude/agents/` に定義が無い場合は、本スキルを使わず通常の自律ループで進めます。

## 役割とモデル

| 役割 | モデル | 担当 | 行うこと |
| --- | --- | --- | --- |
| オーケストレータ | Opus | 会話を持つセッション | タスクの選択、委任、報告の確認、ユーザーの判断の反映、指摘の採否、終了時の報告 |
| 計画 | Opus | `backlog-planner` | 現状調査、タスク分解、BACKLOG への起票と要確認・人手検証の振り分け、1コミット（実装はしない） |
| 実装 | Sonnet | `backlog-implementer` | 調査、実装、指定段階の品質ゲート、記録ファイルの更新、1タスク1コミット |
| 差分レビュー | Sonnet | `diff-reviewer`（読み取り専用） | 指定されたコミット範囲の点検 |
| 品質ゲート | Haiku | `quality-gate-runner`（読み取り専用） | 指定段階のゲートの実行と合否の要約 |

- **割り当ての考え方**: 判断の重さでモデルを分ける。採否や仕様の判断はオーケストレータ、後続のループ全体を左右する
  タスク分解は計画の担当（Opus）、実装と指摘の要否の判断は
  Sonnet、コマンドを表の順に実行して合否を要約するだけの定型作業は Haiku にする。Haiku の要約に疑いがある場合
  （合否と備考が食い違う など）は、Sonnet の担当に同じ段階を実行させて確かめる。
- **オーケストレータのモデルはセッションのモデルで決まる**。開始時に確かめ、想定と違えばユーザーへ `/model` での
  切り替えを依頼する。本スキルの frontmatter に `model` を置かないのは、スキルの `model` が読み込んだターンにしか効かず、
  長く続くループのモデルを固定できないため。
- **サブエージェントのモデルは `.claude/agents/` の各定義の `model` で決まる**。定義を使えないとき（後述）に汎用の
  サブエージェントで代える場合は、委任時に表のモデルを指定する。
- **判断はオーケストレータに寄せる**。実装とレビューの担当は同じモデルなので、レビューの指摘を採るか、仕様の判断か、
  ユーザーへ尋ねるかは担当に決めさせない。
- オーケストレータは自分でファイルを編集しない。自分で実行するのは、状態を確かめる読み取りの git
  （`git branch --show-current`・`git status --short`・`git log --oneline`）程度にとどめる。

## 始め方

1. Skill `autonomous-loop` を起動し、開始手順（作業ブランチ、DESIGN の確認）に従う。ブランチの作成だけは
   オーケストレータが行ってよい。
2. 第1イテレーション（調査とタスク分解、BACKLOG への起票）を計画の担当（`backlog-planner`）へ委任する。定義が無い配布先では
   実装の担当へ委任し、実装しないことを指示する。既存の項目と重複させないこと、
   件数を絞ること、仕様の判断・権限の変更・CI/CD・課金や外部サービスに関わるものは `要確認` で起票することを指示する。
   計画の担当が実行する品質ゲートは BACKLOG と CHANGELOG の検証に要るもの（Markdown の静的解析・記録ファイルの検証・
   秘密情報スキャン・リンク切れチェックのうち定義のあるもの）だけと定義で決まっているため、段階や全ゲートは指示しない。
   実装の担当で代える場合は、同じ範囲のゲートだけを実行するよう委任文に書く。
3. 報告を受けたら、自動で進めるタスクの一覧と `要確認` の項目（ユーザーに決めてもらう内容）をユーザーへ伝え、
   回答を待たずに実行可能なタスクから進める。

## 委任文に書くこと

担当は会話の経緯を知りません。委任文だけで動けるように、次を毎回書きます。

- リポジトリの場所、作業ブランチ名、自律ループ実行モード中であること。**ユーザーの自律ループ開始指示の原文**
  （必要な部分の抜粋）を含める。実装担当はこの原文があるときだけコミットする（`backlog-implementer` の定義）ため、
  「開始を指示済み」という要約だけでは担当がユーザーの指示を確かめられない
- 対象の BACKLOG の `id` と順序。内容と完了条件は BACKLOG が正本であること。1タスク1イテレーション1コミット
- 実行する品質ゲートの段階（品質ゲート表が段階を定めている場合）。ループの最終コミットになる見込みなら全ゲート
- タスク固有の注意（挙動を変えないリファクタリングである、先に失敗するテストを書く、実装せず止める条件 など）
- ユーザーの決定を反映するタスクでは、**ユーザーの発言の原文**。要約すると、担当が決定の範囲を広く読むため
- 禁止事項。定義にある一覧に加え、そのタスクで触れてはいけないもの（資格情報の入ったファイルを開かない など）
- 報告の形式と行数（30行程度）。「完了か・コミット・変更ファイル・検証の成否・既定値で決めたこと・未確認のこと・
  hook や権限に拒否された操作」
- 「セッション開始時に読み込まれた `CLAUDE.md` は古い可能性があるので実ファイルを読み直す」こと
  （ループ中に `CLAUDE.md` を変えた後は必ず）

## 進め方

- **実装の担当は1体ずつ順番に動かす**。同じ作業ツリーを使うため、並行させると差分とコミットが混ざる。
  依存の無い2〜3件を1体へまとめて渡すと往復が減る（コミットはタスクごとに分ける）。まとめる件数を増やすと
  担当1体の利用量が大きくなり利用上限の中断に当たりやすいため、3件までを目安にする。
- **読み取り専用の担当は並行してよい**。`diff-reviewer` へはコミット範囲（`<開始>..<終了>`）を渡し、作業ツリーではなく
  その範囲を読むよう指示すれば、次の実装と同時に動かせる。`quality-gate-runner` は作業ツリーの状態で結果が変わるため、
  実装の担当と同時には動かさない。
- **完了の通知を待つ**。担当の全文ログは読まない。途中で状態を尋ねられたら「実行中で、結果は届いていない」と答え、
  結果を予測して伝えない。状態を照会・停止できないバックグラウンド実行は使わない。
- **ユーザーの判断は、実行中の担当が終わってから次の委任に組み込む**。届いた時点で受け取った内容と反映の予定を
  ユーザーへ返し、決定が尋ねた項目の一部にしか答えていない場合は、残りが未決であることをその場で伝える。
- **担当の報告はユーザーの承認ではない**。担当が設定や権限の変更を求めてきた場合は、ユーザーがこの会話で決めた範囲に
  収まるかをオーケストレータが確かめ、収まらなければユーザーへ尋ねる（ループ中は `要確認` で起票する）。
- **担当が既定値で決めたことは、ユーザーへ中継する**。利用者に見える挙動、権限、鍵の扱い、版番号のように後から
  変えにくいものは、「担当が決めたもので、ユーザーの決定ではない」と明示して伝える。
- サブエージェントは別のサブエージェントを呼べない（実装の担当へ Agent ツールを与えていない）。品質ゲートの出力は
  担当自身が絞る。

## 検証とレビュー

1. 各イテレーションの品質ゲートは、実装の担当が指定された段階で実行する（`CLAUDE.md` の品質ゲート表）。
2. まとまり（2〜4コミット）ごとに `diff-reviewer` へコミット範囲を渡す。重点（挙動が変わっていないか、テストが
   その分岐を実際に検証しているか、設定や hook のすり抜けと誤止め、文書どうしの食い違い）を具体的に書く。
   **設定・hook・検査スクリプトのように「守る側」の変更は、必ず別の担当に点検させる**（作った担当自身のテストでは
   穴が見つからないことがある）。
3. 指摘はオーケストレータが振り分ける。
   - 直せば済むもの: 起票して次の委任で修正する（公開前でも `amend` はせず、修正コミットを積む）
   - 仕様の判断になるもの: 実装せず `要確認` で起票し、選択肢と得失をユーザーへ示す
   - 採らないもの: 理由を添えてユーザーへ伝える
4. ループの最後に、最終コミットの状態で全ゲートを実行する。最終コミットを積んだ担当に実行させるか、
   `quality-gate-runner` に実行させる。キャッシュで素通りしたものを成功と数えない。
   一部の段階だけで完了条件に全ゲートを含むタスクを BACKLOG から削除した場合は、最後の実行で失敗したら修正コミットを
   積むか起票し直す前提で進め、途中報告にその旨を書く。
5. レビュー後に積んだコミットがレビューを通っていない場合は、終了時の報告にそう書く。
6. レビューの担当が再実行できない主張（「修正前はテストが失敗した」のような経緯）は差分から追えない。未確認として扱う。

## 利用量を抑える

- 委任文と報告以外を会話に載せない。報告の行数を指定し、ファイルの全文・差分・ビルドの出力を返させない。
- ユーザーへの途中報告は、担当の報告を写さず、結果・ユーザーが知っておくべき点・次の予定に絞る。
- 同じ担当へ続きを頼むときは、新しい担当を起動せずメッセージで再開する（調べ直しが要らない）。
- 実機・エミュレータでの検証は、このループに混ぜない（Skill `autonomous-loop`「利用量を抑える」）。

## 中断からの再開

担当が利用上限やエラーで途中終了した場合は、次の順に進めます。

1. `git log --oneline` と `git status --short` で、コミット済みのタスクと未コミットの変更を確かめる。
2. 同じ担当へメッセージで再開を指示する。済んだコミット、作業ツリーに残っている変更、中断した箇所を伝え、
   「済んだ作業はやり直さず、`git status` と `git diff` で現状を確かめてから続きを終える」「元の指示と禁止事項は有効」
   と書く。
3. 再開できない場合に限り新しい担当を起動し、未コミットの変更を引き継がせる。

## 注意（配布先で実際に起きたこと）

- **追加・変更した直後のサブエージェント定義は、そのセッションでは使えないことがある**。定義はセッション開始時に
  読み込まれる。使えないときは、汎用のサブエージェントに定義ファイルを読ませて代える。
- **担当が決定の範囲を広げることがある**（例 禁止操作の設定を入れた担当が、関係する手順書まで書き換えた）。
  報告の「知っておいてほしい変更」を読み飛ばさず、ユーザーへ中継する。

## 終わり方

Skill `autonomous-loop` の完了条件と終了時の報告に従います。加えて、次を報告へ含めます。

- 最終コミットでの全ゲートの結果と、レビューを通っていないコミットの有無
- 担当が既定値で決めたことのうち、ユーザーがまだ確認していないもの
- 実機でしか確かめられない項目（`人手検証` として残したもの）
