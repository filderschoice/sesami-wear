# 実機検証手順（Sesami Wear）

`docs/records/managed/BACKLOG.md` の `区分: 人手検証` は「自動品質ゲートの合否判定から除外する」項目だが、
**「Claude Code には検証できない」という意味ではない**。多くはデモモード・ダミー資格情報・モック API で
実機上まで確認でき、実際に BL-126 の11項目中9項目はこの手順で検証できた（2026-09-16）。

## 0. 最重要原則

1. **実機検証を依頼されたら、まず adb での実機接続を試す。** エミュレータの用意やユーザーへの
   手動確認依頼より先に、`adb-device-connection` スキルの手順（`adb kill-server` → `start-server` →
   mDNS 自動検出）で実機に繋がらないかを確認する。本リポジトリの検証対象は Pixel 8 Pro（スマホ）と
   Pixel Watch 2（ウォッチ）の2台で、どちらもペア設定済みなら mDNS で見つかる。
2. **実資格情報（apikey / secretKey）は扱わない。** 本人に入力してもらうのも避ける。代わりに
   デモモード・ダミー資格情報・モック API（第3節）で状態を作る
   （`rules/guardrails-unified.v1.md` 12.5）。
3. **Play ストア版を消さない。** 入れ替えると保存済みの資格情報が消える。併存インストール（第2節）を使う。
4. **検証後は必ず後始末する**（第7節）。ダミー資格情報の削除、モックサーバーの停止、
   ウォッチの画面消灯設定の復元。

## 1. 検証できる範囲の見取り図

| 検証したいこと | 使う仕掛け | 実資格情報 |
| --- | --- | --- |
| 画面遷移・表示文言・ウィジェット設置・設定画面 | デモモード（登録0台） | 不要 |
| デバイス一覧・選択画面・「全デバイス」の出現条件・削除後の復帰 | ダミー資格情報（API は呼ばない操作のみ） | 不要 |
| 施錠/解錠の成功、状態同期（ウィジェット⇔Tile）、MIXED 表示、一括操作 | モック API（第3節） | 不要 |
| 実 Sesame デバイスの物理動作、Sesame API との本番疎通 | — | **必要（人手検証として残す）** |

**デモモードでは状態同期を検証できない。** デモの状態はウィジェットと Tile で意図的に独立している
（mobile はデモ時に DataItem 同期を行わず、wear のデモは `MessageClient` へ送らない）。
これは仕様であり不具合ではないので、同期の検証にはモック API を使う。

## 2. Play 版と併存させてデバッグ版を入れる

実機には Play ストア版（リリース署名）が入っているため、デバッグ署名のビルドでは
**上書き更新できない**（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。debug ビルドには
`applicationIdSuffix = ".debug"` が付いており（BL-131）、`com.sesamiwear.mobile.debug` として
併存インストールされる。アプリ名も `Sesami Wear (debug)` へ上書きされ、ランチャー・
ウィジェット選択画面・ウォッチのアプリ一覧で Play 版と区別できる。

```bash
ANDROID_SERIAL=<スマホのシリアル>  ./gradlew :mobile:installDebug
ANDROID_SERIAL=<ウォッチのシリアル> ./gradlew :wear:installDebug
```

- **mobile と wear の双方へ同じサフィックスが付いている必要がある。** Data Layer API は
  ノード間で `applicationId` と署名の一致を要求するため、片方だけ debug 版にすると連携しない。
- インストール後は `adb -s <シリアル> shell dumpsys package com.sesamiwear.mobile.debug` で
  `lastUpdateTime` が今回の時刻になっていることを確認する（`adb-device-connection` 第6節）。

## 3. モック API で「施錠/解錠の成功」を作る

実 Sesame デバイスが無いと状態が変わらず、状態変化を起点とする同期（ウィジェット⇔Tile）を
検証できない。`mobile` の debug ビルドは接続先を差し替えられる（BL-132）。

```bash
# 1) PC 側でモックを起動（標準ライブラリのみ、状態はメモリ保持、署名は検証しない）
python scripts/mock-sesame-api.py

# 2) 接続先を差し替えてインストール。IP は実機から見た PC のアドレス
ANDROID_SERIAL=<スマホのシリアル> \
  ./gradlew :mobile:installDebug -PsesameApiBaseUrl=http://<PCのIP>:8080/api/sesame2
```

- `-PsesameApiBaseUrl` を渡さなければ本番 URL のまま。リリースビルドでは値が空になる。
- 平文 HTTP は debug 専用マニフェストでのみ許可されている。
- uuid は任意の文字列でよい。ダミー資格情報の uuid をそのまま使う。
- **モックのログが検証の証跡になる。** `[mock] POST <uuid> cmd=83 -> unlocked` のように、
  どの端末の操作が実際に実行口まで届いたかを1行で確認できる。スクリーンショットと
  突き合わせて記録へ残す。
- PC がテザリング親機の場合、実機から見た PC のアドレスはテザリング側（例 `192.168.137.1`）で、
  `ipconfig` に出る LAN 側のアドレスとは異なる。

## 4. ウォッチ側の準備

### Tile をカルーセルへ追加する

ウォッチの UI を辿らずに、デバッグ面のブロードキャストで追加できる。

```bash
adb -s <ウォッチ> shell am broadcast -a com.google.android.wearable.app.DEBUG_SURFACE \
  --es operation add-tile \
  --ecn component com.sesamiwear.mobile.debug/com.sesamiwear.wear.tile.SesameTileService
# → Broadcast completed: result=1, data="Index=[0]" （Index が挿入位置）
```

`--es operation remove-tile` で取り外せる。**Play 版の Tile とは別インスタンス**なので、
利用者が使っている Tile の設定は変わらない。

### Tile まで移動する

文字盤から左スワイプでタイルへ進む。`KEYCODE_HOME` は状況によりアプリ一覧を開くので、
開いてしまったら `KEYCODE_BACK` で閉じてから改めてスワイプする。

```bash
adb -s <ウォッチ> shell input keyevent KEYCODE_WAKEUP   # 一連の操作の開始前に1回だけ
adb -s <ウォッチ> shell input swipe 350 192 60 192 200  # 画面は 384x384
```

- **文字盤を不用意にタップしない。** 利用者の文字盤には Play 版の Complication が載っている
  ことがあり、タップすると**実際の鍵が動く**。
- 画面消灯対策（`screen_off_timeout` の一時延長と復元）は `adb-device-connection` 第6.5節に従う。
- ウォッチは画面消灯で Wi-Fi ごとスリープし、adb から消える。復帰は利用者に画面を点けてもらう
  必要がある。長い検証は**ウォッチ側を先に**済ませると待ちが減る。

### 検証の証跡

`adb -s <ウォッチ> logcat -d | grep -E 'SesameTileService|Vibrator'` で、
`buildConfiguredTile tileId=<id> nodeId=true state=UNLOCKED` と振動の発火を確認できる。
ハプティクスはスクリーンショットに写らないため、ログが唯一の証跡になる。

## 5. スマホ側の UI 自動操作

- **ウィジェットの設置はタップではなくドラッグ＆ドロップ。** ウィジェット選択画面でプレビューを
  タップしても何も起きない。`adb shell input draganddrop <x1> <y1> <x2> <y2> 2500` で
  ホーム画面へ落とすと、設定 Activity（対象デバイス選択）が開く。
- ランチャーによってはウィジェット一覧に検索欄がある。`input tap` で検索欄を開き `input text`
  で絞り込むとスクロールせずに到達できる。`KEYCODE_BACK` を押すと検索がリセットされるので、
  絞り込んだ直後に対象をタップする。
- **`input text` は文字を取りこぼす。** 連続する同じ文字やハイフンが欠けることがある
  （`00000000-0000-4000-...` が `00000000-000-400-...` になる等）。入力後は必ず
  スクリーンショットで実際に入った文字列を確認し、ダミー値なら「欠けたまま使う」判断でよいが、
  **モックと突き合わせる uuid は実際に入った文字列を採用する**。
- 日本語は `input text` で入力できない。表示名などは ASCII で入れる。
- **ホーム画面のページを取り違えない。** スワイプでページを移動したら、必ずスクリーンショットで
  目的のウィジェットがある面かを確認してからタップする。座標だけを信じてタップすると、
  無関係なウィジェット（メディア操作など）を誤操作する。
- スマホは放置すると画面が消灯し、**再点灯後はロック画面**になる。ロック解除は利用者にしか
  できないため、キャプチャが真っ黒／ロック画面だったら解除を依頼する。
- 端末再起動を伴う検証（割り当ての永続化など）では、**再起動後にワイヤレスデバッグが無効に戻る**。
  再起動は検証の最後にまとめ、事前に「再起動後は開発者向けオプションからワイヤレスデバッグを
  ON にしてほしい」と伝えておく。

## 6. 記録の残し方

- 結果は `docs/records/managed/DESIGN.md` の該当機能の節へ `実機検証（ID、日付、機種）` として
  追記する。既存の BL-110 / BL-115 の記述が書式の見本。
- **検証できなかった項目は BACKLOG から消さない。** `状態: 進行中` にして、`完了条件` の末尾へ
  「何が未確認で、なぜ確認できないか」を追記する（`guardrail-records-update` 第2.3節）。
- モックやデモで代替した検証は、**何を代替したかを明示する**。「実機で確認した」とだけ書くと、
  実 Sesame デバイスでの確認が済んだと誤読される。

## 7. 後始末（MUST）

- ダミー資格情報を設定画面から削除する（登録0台へ戻す）。放置すると次回の起動時に
  実在しないデバイスへ通信しようとする。
- モックサーバーを停止する。
- ウォッチの `screen_off_timeout` を元の値（既定 30000）へ戻す。
- 検証用に置いたウィジェット・Tile を残すか外すかは利用者へ確認する。
- `-PsesameApiBaseUrl` 付きでインストールしたデバッグ版が残ることを伝える。本番 URL へ戻すには
  プロパティ無しで入れ直す。

## やってはいけないこと

- 実機に繋がるか試す前に、エミュレータの導入や利用者への手動確認依頼へ切り替える。
- Play ストア版をアンインストールして入れ替える（保存済みの資格情報が消える）。
- 実資格情報を入力する／入力してもらう。
- デモモードで状態同期（ウィジェット⇔Tile）を検証しようとする（仕様上追随しない）。
- ウォッチの文字盤をタップする（Play 版の Complication 経由で実際の鍵が動きうる）。
- `input text` の結果を確認せずに、意図した文字列が入った前提で進める。
- モックやデモで代替した検証を「実機で確認済み」とだけ記録する。
- 検証後にダミー資格情報・モックサーバー・画面消灯設定を残したまま完了報告する。
