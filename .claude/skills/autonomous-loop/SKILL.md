# 自律ループ実行モード 実行手順

人の応答を待たずに複数イテレーションを連続実行するモードの実行手順です。

**前提**: 統制要件（許可・禁止されるgit操作、停止条件、確認事項の非同期化、秘密情報の取り扱い、監査）は
`rules/guardrails-unified.v1.md` セクション12が正本で、セッション開始時に常時読み込まれています。
ブランチ・コミット規約は `CONTRIBUTING.md`「自律ループ実行モードのブランチ・コミット規約」が正本です。
本スキルはそれらを前提とした実行手順のみを定義します。

適用条件（ユーザーによる明示指示があること、スコープ内でのみ有効であること、条件を満たさない場合は
`git add` / `git commit` を実行してはならないこと）は `CLAUDE.md`「自律ループ実行モード」に定義されています。
本スキルが起動された時点で適用条件を再確認してから開始してください。

## 開始手順（MUST）

1. `git branch --show-current` で現在ブランチを確認し、規定ブランチ上であれば
   `feature/loop-<YYYYMMDD>-<主題>` 形式の作業ブランチを作成する
2. `docs/records/managed/DESIGN.md` を読み、対象範囲の既存方針・制約を確認する
   （要件・API仕様の背景が必要な場合は `PLAN.md` も読む。実装済み内容は DESIGN.md が優先）
3. 対象範囲を実行可能な粒度のタスクへ分解し、未登録であれば `docs/records/managed/BACKLOG.md` へ
   登録する（この分解自体を第1イテレーションとして扱う）
4. 自動検証できないタスクは `区分: 人手検証` として登録し、ループの完了判定から除外する。
   本リポジトリでは以下が該当する
   - Pixel Watch実機・Sesame実機を伴う動作確認
   - 実資格情報（apikey / secretKey / uuid）を用いるSesame APIとの疎通確認
   - Google Play Console上の操作（トラック作成、審査提出、テスター管理）

記録ファイルの記述仕様（必須キー・許容値・YAMLの体裁）は `docs/records/spec/FORMAT.md` が唯一の参照元です。
更新前に必ず参照してください。

## イテレーション手順（MUST）

1件のタスクにつき以下を1サイクルとして実行し、次のタスクへ進みます。

1. `BACKLOG.md` から次のタスクを選択する（選択規則は後述）
2. 対象タスクの `状態` を `進行中` へ更新する
3. 実装・テスト追加を行う
4. `CLAUDE.md`「本リポジトリの品質ゲート定義」のコマンドをすべて実行する
5. 失敗した場合は修正し再実行する。同一原因で3回連続して解消できない場合はループを停止する
6. 記録ファイルを更新する（`BACKLOG.md` の完了項目を削除し、コード修正を伴う場合は `EXECUTE.md` へ
   追記、設計方針が変わった場合は `DESIGN.md` を更新、ドキュメント・ルールのみの変更は `CHANGELOG.md`、
   利用者に影響する機能変更・不具合修正は `docs/RELEASE_NOTES.md`）
7. `git status` と `git diff` で差分を確認し、資格情報・個人情報の混入がないことを検査する
8. 作業ブランチへコミットする（1イテレーション1コミット、本文に対象タスクの `id` を列挙）

## タスク選択規則（MUST）

- `状態` が `要確認` またはブロック中のタスクは選択しない
- `依存` に未完了タスクの `id` を含むタスクは選択しない
- 上記を満たすタスクのうち `優先度` が高い順（`P1` → `P2` → `P3`）に選択する
- 同一優先度が複数ある場合は `id` の昇順で選択する
- `区分: 人手検証` のタスクは選択せず、常に保留する

## 確認質問の代替（MUST）

共通規約「確認が必要な場合」は人への確認質問を前提としています。本モードでは確認質問ができないため、
次のとおり非同期化します（guardrails 12.4）。

- 安全性・秘密情報・外部影響に関わる不明点は `docs/records/managed/BACKLOG.md` へ `状態: 要確認` として
  記録し、当該タスクを保留して次の実行可能タスクへ進む
- 安全性判断に関わらない仕様上の不明点は、既定値を選択して `根拠` へ「何を選び、なぜそれで安全か」を
  記録し、続行する
- 「要確認」項目を人の応答なしに自己解決したものとして扱ってはならない

## 出力要件の読み替え（MUST）

共通規約「出力要件」はチャット応答を前提としています。本モードでは人がリアルタイムに出力を読まないため、
以下のとおり出力先を読み替えます。要件そのものは免除されません。

| 対話実行時の出力要件 | 自律ループ実行モードでの読み替え |
| --- | --- |
| 主要ファイルの完全コード・変更対象ファイル一覧・差分の提示 | 実際のファイル編集とコミットをもって充足し、`EXECUTE.md`（コード修正を伴わない場合は `CHANGELOG.md`）へ変更内容・検証コマンドと結果を記録する |
| セットアップ・ビルド・実行・テスト手順 | リポジトリ内のドキュメント（`README.md` 等）へ記載する |
| 要件対応表（対応済み/未対応/対象外） | ループ終了時にまとめて提示し、未対応項目は `BACKLOG.md` に残す |
| コミットメッセージ案の提示 | 実コミットのメッセージ（本文に対象タスクの `id` を列挙）をもって充足する |
| 未確認事項の明示 | `状態: 要確認` として記録し、当該タスクを保留する（人の応答なしに自己解決したものとして扱わない） |
| 人手検証が必要な項目の告知 | `区分: 人手検証` として `BACKLOG.md` へ記録し、完了判定から除外する |

コミットメッセージの形式（Conventional Commits、タイトル行の絵文字、本文に絵文字を含めない）は
共通規約「コミット要件」に従い、本文へ対象タスクの `id` を列挙します。

## 利用量を抑える（MUST）

本モードは1つの会話を長く続けるため、**後半のターンほど1回あたりの入力が大きくなる**
（毎回、会話全体を再送するため）。次の2点を守る。

- **実機・エミュレータでの検証は、実装のループとはセッションを分ける**（`/clear`してから始める）。
  検証で読むスクリーンショットは1枚あたり数百〜数千トークンで、以降のすべてのターンへ乗り続ける。
  検証の手順と節約のしかたは Skill `realmachine-verification` 第8節が正本。
- **調べ物が大きくなる場合はサブエージェントへ渡す。** 中間の出力が本体の履歴に残らない。
  ただしユーザーの明示指示がない限りサブエージェントは使わない方針のため、まず必要範囲を
  絞って読む（ファイル全文ではなく`sed -n`で該当箇所だけ）ことを優先する。

## ループの完了条件（MUST）

以下をすべて満たした時点でループを終了し、ユーザーへ報告します。

- `BACKLOG.md` に `区分: 人手検証` と `状態: 要確認` 以外の未完了タスクが存在しない
- `CLAUDE.md`「本リポジトリの品質ゲート定義」のコマンドがすべて成功している
- `DESIGN.md` が実装済み内容と整合している

停止条件（禁止操作への到達、品質ゲートの同一原因3回連続失敗、実行可能タスクの枯渇など）に該当した場合も
ループを終了し、到達した停止条件を明示して人へ引き継ぎます（guardrails 12.3）。

## 終了時の報告（MUST）

- 実施した内容の要約と、要件対応表（対応済み/未対応/対象外）
- 残存する `要確認` 項目と `人手検証` 項目の一覧
- 作成した作業ブランチ名と、`git push` およびプルリクエスト作成のコマンド例
- プルリクエスト説明文の案（`.github/instructions/pr.instructions.md` の構成に従う）

`git push` とプルリクエストの作成は、モードを問わず常にユーザーが実行します。
